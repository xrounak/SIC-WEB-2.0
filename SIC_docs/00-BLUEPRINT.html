SIC Nexus 2.0 Blueprint

Schema, features, pages and user flows for the first release. Business rules carry over from v1 and the SIC_docs spec. Experience, flows and UI are new; visual design is pending inspiration references.

Architecture

The browser never holds a privileged key. Server Components read data as the signed-in user, so Row Level Security decides what comes back. Every write that changes a status, a role or a seat count goes through one Postgres function. That function checks permission, validates the transition and writes the audit row in the same transaction.

flowchart LR
  U["Browser"] --> MW["Next.js middleware: refresh session, gate /portal and /manage"]
  MW --> RSC["Server Components: reads as the user"]
  MW --> SA["Server Actions: Zod validation, then RPC"]
  RSC --> PG[("Postgres with RLS")]
  SA --> RPC["SECURITY DEFINER RPCs: transitions, registration, roles"]
  RPC --> PG
  RPC --> OB["email_outbox, notifications, audit_logs"]
  OB --> W["Vercel cron / route handler sends email via provider"]
  U --> AUTH["Supabase Auth: Google, OTP, password"]
  U --> ST["Supabase Storage: public-media, avatars, private-docs"]
  • Only the publishable key reaches the browser. The service-role key lives in Vercel server env and is used only by the email worker.
  • Email is written to an outbox inside the same transaction, then delivered separately. A failed send never rolls back a registration or approval.
  • Admin Telegram alerts (from v1) become one more outbox consumer on the server. The bot token never ships to the client.

Identity model

Because everyone has an account, an account no longer means club membership. Three separate fields describe a person, and each changes through its own process.

FieldValuesChanged by
student_statusexternal · unverified · pending · verified · rejectedOnboarding sets pending when a user claims to be our student and gives a roll number. Leadership verifies, usually during recruitment screening.
member_statusnone · applicant · member · alumni · suspendedSubmitting an application sets applicant. A selected decision sets member. Leadership handles alumni and suspension.
user_rolesteam_lead · vice_president · president · faculty_coordinator · adminAdmin only, through assign_role. Audited. Lead scope comes from team_members.team_role = 'lead', not from the role alone.

Naming: teams are the club's standing units (Robotics, Media, PR). event_teams are groups that register together for one event. They never share a table.

Schema

Every table uses a uuid key, timestamptz times, RLS enabled and deny by default. Public pages use slugs. Important records are archived, not deleted. Each area below becomes its own migration file.

Status machines

Only RPCs change these columns. The browser sends an intent such as approve, publish or withdraw, never a status value.

Event

stateDiagram-v2
  [*] --> draft
  draft --> pending_review : submit
  pending_review --> changes_requested : lead asks changes
  changes_requested --> pending_review : resubmit
  pending_review --> rejected : lead rejects
  pending_review --> lead_approved : lead approves
  lead_approved --> published : publish, minor event
  lead_approved --> final_approved : VP or President approves, major event
  lead_approved --> changes_requested : final reviewer asks changes
  lead_approved --> rejected : final reviewer rejects
  final_approved --> published : publish
  published --> cancelled : cancel and notify registrants
  published --> completed : after ends_at
  completed --> archived
  rejected --> [*]

Event team and invite

stateDiagram-v2
  [*] --> forming : leader creates team
  forming --> complete : accepted members reach team_min
  complete --> forming : member withdraws below team_min
  forming --> withdrawn : leader withdraws
  complete --> withdrawn : leader withdraws
  forming --> withdrawn : registration closes while incomplete

Invite: pending to accepted, declined, revoked by the leader, or expired at reg_closes_at.

Application

stateDiagram-v2
  [*] --> submitted
  submitted --> screening
  screening --> shortlisted
  screening --> rejected
  shortlisted --> interview
  interview --> selected
  interview --> waitlisted
  interview --> rejected
  waitlisted --> selected
  submitted --> withdrawn : applicant withdraws
  screening --> withdrawn : applicant withdraws

Applicants see a simpler status: Received, Under review, Interview, Decision. Internal stages and notes stay private.

Project: draft → submitted → in_review → published or rejected, with changes_requested going back to draft. Published projects can be archived.

Resolved questions

The defaults in grey were accepted on 28 Oct 2026 and are built into the migrations. Incomplete teams are reminded and withdrawn by run_scheduled_maintenance(), which a Vercel cron calls.

  1. Which events count as major and need VP / President approval?Default: hackathons, competitions, external events, and anything with capacity over 100. The lead can also flag any event.
  2. What happens to teams still under team_min when registration closes?Default: they are withdrawn automatically and the leader is emailed 24 hours before close.
  3. Must the account email match the invited email?Default: yes, which stops forwarded links being used. The leader can re-invite a different address.
  4. Who verifies students, and with what proof?Default: any lead or VP / President, using the roll number checked against the college list. No ID-card uploads, to avoid storing documents.
  5. Capacity in P0, waitlist in P1?Default: a hard capacity cap in P0. The waitlist arrives with attendance in P1.
  6. Email providerDefault: Resend's free tier (3,000 emails a month) with a verified club domain. Supabase SMTP handles auth emails only.
  7. Keep the admin Telegram alerts from v1?Default: yes, sent from the server for new proposals and applications.
  8. Import v1 data?Default: start empty. Optionally import past v1 events and gallery images as archived content.
  9. Can external participants see members-only events?Default: no. Visibility members means member_status = member.

Before anything else: revoke the v1 Telegram bot token in BotFather. It ships in the v1 JavaScript bundle and anyone can read it.
